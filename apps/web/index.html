GitHub Actions · self-hosted · disposable

Your machine.
Their CI.
One command.

gh-runner temporarily registers the computer you're sitting at as a self-hosted runner for the repo you're standing in. It stays online for as long as the command runs, taking job after job — then deregisters and deletes everything it downloaded.

Some jobs only make sense on your hardware

Apple silicon, for real

Build and test on the exact M-series machine on your desk instead of paying for a hosted macOS minute — or emulating it and hoping.

The GPU you already own

CUDA suites, model evals, anything that wants a real accelerator. Add --labels gpu and target it from your workflow.

Behind the VPN

Integration tests that need a staging database, an internal registry, or a device on your LAN. Your machine is already on the network.

Debug a job, live

Reproduce a failing workflow step in the same shape CI runs it — but on a box where you can attach a debugger and read the filesystem afterwards.

Skip the queue

A four-minute hosted job is often twenty seconds locally. Warm caches, warm disk, no waiting for a runner to be allocated.

Zero standing infrastructure

Nothing is installed as a service. Nothing survives the run. There's no runner sitting idle in your repo settings a month from now.

Pick your platforms, or just name them

Run it with no arguments and it asks. Your own OS comes pre-ticked, so the common case is one keypress; anything this machine can't be is shown with the reason and can't be selected. 

$ gh-runner            # pick from a menu
$ gh-runner linux      # or name them
$ gh-runner mac linux  # one runner each, in parallel
$ gh-runner --all      # everything this machine can serve
$ gh-runner --os mac,linux

Impossible is an error

Ask a Mac for a Windows runner and the command stops, with the reason — rather than quietly registering something that can never run those jobs. 

$ gh-runner windows
error: this machine can't run that runner
       Windows: needs a Windows machine

--all never errors

It takes what's possible on this host and ignores the rest — macOS and Linux on a Mac, Linux alone on a Linux box, Windows and Linux on a PC.

Several runners, one command

Each platform gets its own runner, its own labels, and its own cleanup, all running in parallel. Their output is prefixed so you can tell them apart.

No pointless prompts

When there's only one possible answer — a Linux box, or a Mac with Docker stopped — it doesn't ask. It logs what it's serving and why the rest are out, then gets on with it.

Scriptable

With no terminal to prompt on and no platform named, it serves this machine's own OS — so a cron job or a CI script never blocks waiting for an answer.

How it works

  1. Checks your setup

    Requires gh to be installed and authenticated. Your credentials stay in the GitHub CLI — this tool never handles a long-lived token.

  2. Resolves the repo

    Detected from the git checkout you're standing in, or set explicitly with --repo owner/name. Public repos are refused by default.

  3. Audits your workflows

    Reads .github/workflows and reports which jobs will actually land here — and offers to open a PR when none of them would.

  4. Fetches the runner

    Downloads the matching actions/runner release for your OS and architecture, cached under ~/.cache/gh-runner for next time.

  5. Registers a runner

    Mints a short-lived registration token and configures the runner in a fresh temp directory under the gh-runner label.

  6. Runs your job

    Any job with runs-on: [self-hosted, gh-runner] lands here. Same label on every machine, so the YAML doesn't care whose laptop showed up.

  7. Cleans up after itself

    Deregisters and deletes the temp directory — on success, on failure, and on Ctrl+C. Nothing survives the command: no daemon, no service, no leftover registration.

In your workflow

One label, every machine. Drop it into runs-on and any registered runner picks the job up: 

jobs:
  build:
    runs-on: [self-hosted, gh-runner]
    steps:
      - uses: actions/checkout@v5
      - run: npm ci && npm test

Need a specific OS? Ask for one

Every machine also registers a label pinned to its operating system, so a job that needs macOS never lands on the Linux box someone else has online:

Label Registered on Use it when
gh-runner every machine the job doesn't care where it runs
gh-runner-mac macOS only the job needs macOS
gh-runner-linux Linux only the job needs Linux
gh-runner-windows Windows only the job needs Windows
<hostname> that one machine the job needs your box specifically

Where Linux comes from

Ask for linux on a Mac or a Windows box and the runner goes into a Docker container, registering exactly the labels a real Linux machine would. Nothing is unpacked on your host, and the job can't see your filesystem — no volumes, no Docker socket.

Your machine Its own OS gh-runner linux Still can't provide
macOS gh-runner-mac gh-runner-linux Windows
Linux gh-runner-linux native, or sandboxed macOS, Windows
Windows gh-runner-windows gh-runner-linux macOS

Docker cannot get you macOS or Windows. macOS containers don't exist — there's no macOS container runtime, and Apple's licence only permits macOS virtual machines, on Apple hardware. Windows containers share the host kernel, so they only run on Windows. Full three-OS coverage is a Mac and a Windows box, with Docker covering Linux from either, so you don't need a third machine.

One machine, one OS (plus Linux)

gh-runner serves platforms this machine can actually be. On an Apple silicon MacBook that's macOS natively and Linux in a container — never Windows. Asking for Windows there is an error, not a silent fallback. To cover it you need a Windows machine; that's a hardware fact, not a missing feature.

It checks that before it starts

Registering a runner nothing targets is the easiest way to waste ten minutes. On startup, gh-runner reads every workflow and tells you which jobs will actually land here — then offers to fix the ones that won't. 

==> Checking .github/workflows for a matching runs-on...
    ! no job targets this runner; 3 target GitHub-hosted runners

Update 3 jobs to runs-on: [self-hosted, gh-runner] and open a pull request? [y/N] y

==> Preparing a workflow fix on gh-runner/target-self-hosted...
    ✓ .github/workflows/ci.yml → build now targets this runner
    Pull request opened: https://github.com/octocat/thing/pull/42

Your working tree is never touched

The rewrite happens in a throwaway git worktree checked out from your default branch. Staged changes, unstaged edits, and your current branch all stay exactly as they were — the worktree and its branch are removed on every exit path.

It reads YAML properly

A real YAML parser, not a regex. Anchors and aliases resolve the way GitHub sees them, a runs-on: inside a shell script is ignored, and a malformed file is reported rather than silently mis-read. When the value is a ${{ }} expression it says so instead of guessing.

It only changes what it should

Only GitHub-hosted jobs get repointed. A job already asking for self-hosted with labels you lack is left alone — that one's fixed with --labels, not a PR.

You stay in charge

It asks before doing anything. --fix-workflows skips the prompt, --no-fix-workflows silences the offer, and --fix-jobs a,b narrows it to specific jobs.

Options

Flag What it does
--once Take one job, then deregister (default: stay online)
--labels a,b,c Extra labels in addition to gh-runner and the host label
--repo OWNER/NAME Target a specific repo instead of detecting from the current directory
--name NAME Runner name to register (default <host>-<pid>)
--allow-public Permit registration on a public repo — see below
--all Serve every platform this machine can
--os a,b Platforms to serve (same as positional arguments)
--docker-image IMAGE Image for containerised runners (default GitHub's runner image)
--docker-platform P Container platform, e.g. linux/amd64
--runner-version X.Y.Z Pin the runner version (default: latest release)
--cache-dir PATH Where to cache downloaded runner archives
--no-workflow-check Skip the runs-on audit of .github/workflows
--fix-workflows Open the workflow PR without asking first
--no-fix-workflows Never offer to open it
--fix-jobs a,b Limit the fix to these job ids
--fix-label LABEL Label the fix PR writes (default gh-runner)

Safety

Public repos are refused by default

On a public repo, anyone can open a pull request — and a workflow that triggers on pull_request would run their code on your machine, as your user. That is not a hypothetical; it's the standard self-hosted runner warning in GitHub's own docs.

--allow-public exists as a deliberate escape hatch for repos where you trust every single person who can open a PR. Reach for it on purpose, not by habit.

  • Lives with the command — stop the command and the runner is gone; --once makes it ephemeral so GitHub retires it after a single job.
  • Fresh temp directory — the runner's work tree is created with mktemp -d and removed on exit.
  • Cleanup on every path — normal exit, error, and Ctrl+C all deregister.
  • No token handling — registration and removal tokens are minted on demand through gh and live for minutes.
  • Admin rights required — you can only register a runner on a repo you already administer.

Try it in the repo you have open

Requires gh, authenticated with gh auth login, plus admin rights on the target repo. macOS, Linux and Windows, on x64 and arm64.
