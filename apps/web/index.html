gh-runner registers the computer you're sitting at as a self-hosted runner for the repo you're standing in. It takes jobs for as long as the command runs, then deregisters and deletes everything it downloaded.

Some jobs only make sense on your hardware

Apple silicon & your GPU

Build on the M-series machine on your desk; run CUDA suites on the card you already own. Add --labels gpu and target it from your workflow.

Behind the VPN

Integration tests that need a staging database, an internal registry, or a device on your LAN. Your machine is already on the network.

No queue, no infrastructure

Warm caches instead of a four-minute hosted job — and nothing installed as a service, nothing sitting idle in your repo settings next month.

Usage

Run it with no arguments and it asks, with your own OS pre-ticked. Platforms this machine can't be are shown with the reason and can't be picked — asking for one outright is an error, not a silent fallback. 

$ gh-runner            # pick from a menu
$ gh-runner mac linux  # one runner each, in parallel
$ gh-runner --all      # everything this machine can serve
$ gh-runner --once --labels gpu --repo owner/name

Other flags: --name, --allow-public, --docker-image, --docker-platform, --runner-version, --cache-dir, and the workflow-check switches below. gh-runner --help lists them all.

It checks your workflows first

Registering a runner nothing targets wastes ten minutes. On startup it parses every workflow — real YAML, not regex — reports which jobs will land here, and offers to open a PR that lets the ones that won't fall back to your machine. Each job keeps its platform: a macos-14 job falls back to gh-runner-mac, so it can only land on a Mac. The rewrite happens in a throwaway git worktree, so your working tree is never touched. 

! no job targets this runner; 3 target GitHub-hosted runners
Update 3 jobs and open a pull request? [y/N] y
Pull request opened: https://github.com/octocat/thing/pull/42

The PR changes nothing about where CI runs until it has to. Each job becomes runs-on: ${{ vars.GH_RUNNER_LINUX || 'ubuntu-latest' }}, and stays on GitHub-hosted runners. Only when GitHub refuses to start hosted jobs — out of minutes, a spending limit, a failed payment — does a running gh-runner set that variable, re-run what was refused on your machine, and clear it again when it stops or the minutes come back. No secret, no extra job, and no self-hosted runner needed the rest of the time.

--fix-workflows skips the prompt, --no-fix-workflows silences the offer, --fix-jobs a,b narrows it, --no-workflow-check skips the audit entirely.

In your workflow

jobs:
  build:
    runs-on: [self-hosted, gh-runner]
    steps:
      - uses: actions/checkout@v5
      - run: npm ci && npm test

Every machine also registers an OS-pinned label — gh-runner-mac, gh-runner-linux, gh-runner-windows — plus its <hostname>, so a job that needs macOS never lands on someone's Linux box. Ask for linux on a Mac or PC and the runner goes into a Docker container with no volumes and no Docker socket. Docker can't give you macOS or Windows, though: there's no macOS container runtime, and Windows containers need a Windows host.

Always on, with Docker Compose

For a server that should always be ready to take jobs, such as a home lab box, a VPS or a Coolify host, run it with Docker Compose. gh-runner is the container's main process, so the runner is online whenever the container is up, restarts with it, and deregisters itself when the container stops. Every release attaches a copy of the file that installs that release's version. 

$ curl -fsSLO https://github.com/singerbj/gh-runner/releases/latest/download/docker-compose.yml
$ printf 'GH_TOKEN=%s\nGH_RUNNER_REPO=%s\n' "github_pat_…" "you/your-repo" > .env
$ docker compose up -d
$ docker compose logs -f   # wait for "Runner is live"

On Coolify: add a Docker Compose Empty resource, paste the file, set GH_TOKEN and GH_RUNNER_REPO under Environment Variables, and deploy. It needs no domain or port.

  • Token: a fine-grained token for that one repo, with Administration, Actions and Variables set to read/write. The repo must be private.
  • Options: GH_RUNNER_NAME (default gh-runner-docker), GH_RUNNER_LABELS for extra labels, and GH_RUNNER_VERSION to install a specific version.
  • Linux only. Jobs run as an unprivileged user inside the container, with no Docker socket and nothing from the host mounted. That keeps them away from anything else on the server, but it also means docker build, services: and container: jobs won't run there.

Every job on it can read the token

The runner passes its environment on to the jobs it runs, GH_TOKEN included. Scope the token to the one repo, and only point it at a repo where you trust everyone who can push.

Safety

Public repos are refused by default

Anyone can open a pull request on a public repo, and a pull_request workflow would run their code on your machine, as your user. --allow-public is a deliberate escape hatch for repos where you trust everyone who can open a PR.

  • Lives with the command — stop it and the runner is gone; --once retires it after a single job.
  • Cleans up on every path — normal exit, error and Ctrl+C all deregister and delete the temp work tree.
  • No token handling — registration tokens are minted on demand through gh and live for minutes.
  • Admin rights required — you can only register on a repo you already administer.

Try it in the repo you have open

Requires gh, authenticated with gh auth login, plus admin rights on the target repo. macOS, Linux and Windows, on x64 and arm64.
